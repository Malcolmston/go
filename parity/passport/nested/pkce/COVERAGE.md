# `passport/pkce` vs `pkce-challenge` — API inventory

Nested harness. `parity/passport/` scores the passport port itself; this
directory scores the nested `github.com/malcolmston/passport/pkce` package
against its own upstream, the npm implementation of RFC 7636 Proof Key for Code
Exchange.

- upstream oracle: **`pkce-challenge@6.0.0`** (pinned in `node/package.json`)
- port: `github.com/malcolmston/passport/pkce` (`replace` → `../../../../passport`)
- score: `parity.json`, regenerated by `GOWORK=off go test .`

## How the upstream list was derived

Mechanically, by reflecting over the installed package:

```sh
cd node && node -e 'const m = await import("pkce-challenge");
for (const k of Object.keys(m).sort()) console.log(k, typeof m[k], m[k].length)'
```

which prints exactly:

```
default function 2          # pkceChallenge(length, method)
generateChallenge function 1  # (code_verifier, method = "S256")
verifyChallenge function 2    # (code_verifier, expectedChallenge, method = "S256")
```

That is the entire public surface: three functions. The Go side was enumerated
with `GOWORK=off go doc -all ./pkce` in the passport submodule.

None. `pkce` matched the oracle everywhere the two implementations attempt the

## Deviations

All 7 sit in the `verify` group and share one root cause, recorded per case in
`cases/verify.json` and in `passport/API-DEVIATIONS.md`:

`verifyChallenge` re-derives the challenge and compares strings, and validates
nothing about the verifier. RFC 7636 §4.1 fixes the verifier at 43–128
characters from the unreserved set `[A-Za-z0-9-._~]`, and §4.6 requires the
server to validate the value it receives. `pkce.Verify` performs that check
first, so it refuses:

| case | verifier | upstream | port |
| --- | --- | --- | --- |
| `vf-plain-both-empty` | `""` against challenge `""` | **accepts** | rejects |
| `vf-s256-verifier-empty` | `""` | accepts | rejects |
| `vf-s256-verifier-too-short` | 42 chars | accepts | rejects |
| `vf-plain-too-short` | 42 chars | accepts | rejects |
| `vf-s256-verifier-too-long` | 129 chars | accepts | rejects |
| `vf-s256-verifier-bad-charset` | 43 chars containing `+` | accepts | rejects |
| `vf-s256-verifier-unicode` | non-ASCII | accepts | rejects |

`vf-plain-both-empty` is the one worth spelling out: under the `plain`
transformation the challenge *is* the verifier, so an upstream deployment that
stored an empty `code_challenge` is satisfied by an empty `code_verifier` and
PKCE stops protecting anything. The port refuses an empty challenge outright.
This is deliberately **not** copied.
