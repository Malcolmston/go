# `passport/otpauth` vs `otpauth` (npm) — API inventory

Nested harness. `parity/passport/` scores the passport port itself; this
directory scores the nested `github.com/malcolmston/passport/otpauth` package
against its own upstream — the npm package of the same name, which owns both the
HOTP/TOTP construction and the `otpauth://` key-URI format.

- upstream oracle: **`otpauth@9.5.1`** (pinned in `node/package.json`)
- port: `github.com/malcolmston/passport/otpauth` (`replace` → `../../../../passport`)
- score: `parity.json`, regenerated by `GOWORK=off go test .`

## How the upstream list was derived

Mechanically, by reflecting over the installed package:

```sh
cd node && node -e '
const m = await import("otpauth");
console.log("exports:", Object.keys(m).sort().join(" "));
for (const c of ["TOTP","HOTP","URI","Secret"])
  console.log(c, "static:", Object.getOwnPropertyNames(m[c]).join(" "),
                 "| proto:", Object.getOwnPropertyNames(m[c].prototype).join(" "));'
```

which prints exactly:

```
exports: HOTP Secret TOTP URI version
TOTP  static: defaults counter remaining generate validate | proto: constructor counter remaining generate validate toString
HOTP  static: defaults generate validate                   | proto: constructor generate validate toString
URI   static: parse stringify                               | proto: constructor
Secret static: fromLatin1 fromUTF8 fromBase32 fromHex       | proto: constructor buffer latin1 utf8 base32 hex
```

The Go side was enumerated with `GOWORK=off go doc -all ./otpauth` in the
passport submodule.

## Port fixes this harness produced

| case | before | after |
| --- | --- | --- |
| `parse-invalid-secret` | `Parse` accepted `secret=not-base32!!`, storing a credential that could never produce a code (the failure surfaced later, inside `Code`) | the secret must decode as base32 for the URI to parse |
| `parse-hotp-without-counter` | an `otpauth://hotp/...` URI with no `counter` parsed, silently assuming 0 | `counter` is REQUIRED for `hotp` by the Key Uri Format, as upstream also insists; a URI without it is now an error |

Both are asserted in `otpauth/otpauth_test.go` (`TestParseErrors`).

## Deviations

All 8 are recorded per case in `cases/*.json` and in
`passport/API-DEVIATIONS.md`. Three families, and in every one the port is the
stricter side:

1. **Digit bounds (3)** — `parse-digits-too-many`, `usable-digits-12`,
   `usable-digits-1`. RFC 4226 §5.3 puts the code length at 6–8 digits; the port
   allows 6–10 (the widest a 31-bit truncated HOTP value fills) and refuses
   anything else. Upstream accepts any count, including a **1-digit** code whose
   entire search space is ten values.
2. **Degenerate keys (2)** — `usable-empty-secret`, `usable-period-negative`.
   Upstream happily generates from an empty shared secret (HMAC with an empty
   key: anybody can compute the code) and from a non-positive period.
   `Key.Validate` refuses both.
3. **Label percent-encoding (2)** — `url-totp-email-account`,
   `url-totp-ampersand-in-issuer`. Upstream runs the label through
   `encodeURIComponent` (`@` → `%40`, `&` → `%26`); the port escapes only what
   the RFC 3986 path grammar requires. The two URIs are equivalent and each side
   parses the other's form, which `parse-totp-encoded-label` confirms.
4. **HOTP replay window (1)** — `verify-hotp-behind-counter`. Upstream's HOTP
   window is symmetric, so a code for an **already consumed** counter verifies
   (`delta: -2`). The port's HOTP window is forward-only, which is what makes a
   consumed counter unreplayable, and is what RFC 4226 §7.4's "move the counter
   forward on success" is for. Deliberately not copied.
