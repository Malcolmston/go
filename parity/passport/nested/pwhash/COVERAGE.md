# `passport/pwhash` vs `pbkdf2` (npm) — API inventory

Nested harness. `parity/passport/` scores the passport port itself; this
directory scores the nested `github.com/malcolmston/passport/pwhash` package
against its own upstream, the npm implementation of PBKDF2 (RFC 2898 / PKCS #5) —
the algorithm the port implements.

- upstream oracle: **`pbkdf2@3.1.6`** (pinned in `node/package.json`)
- port: `github.com/malcolmston/passport/pwhash` (`replace` → `../../../../passport`)
- score: `parity.json`, regenerated by `GOWORK=off go test .`

## Why this oracle

`pwhash` is PBKDF2 (**not** bcrypt, scrypt or argon2 — `pwhash.go` builds on
`crypto/hmac` and the `crypto/sha*` families, with `Key` verified against the RFC
6070 vectors), so the oracle has to be a PBKDF2 implementation. `pbkdf2@3.1.6` is
that, and nothing more: it exports the KDF and no encoding.

Two consequences the reader should hold onto:

1. The **hash is deliberately slow and salted**, so no case ever compares freshly
   generated hashes. Every parameter — salt, iteration count, key length, PRF —
   is a fixed literal, and the `verify` group works the way the task requires:
   against **known derived keys produced by the upstream oracle**, in both
   directions (upstream derives → port verifies; the port's own encoded form is
   assembled around that key and fed to `pwhash.Verify`).
2. The port's **encoded string** (`pbkdf2_<alg>$<iterations>$<b64 salt>$<b64
   derived key>`, a Django-style envelope) has no upstream counterpart in
   `pbkdf2`. It is not left untested: every `verify-*` case runs through it, so
   `Decode`'s validation and `Verify`'s constant-time comparison are exercised —
   what cannot be *compared* is the envelope's literal spelling. A Django-format
   npm oracle (`node-django-hashers`) was evaluated and rejected: it pulls
   `argon2-ffi`, a native module that does not build here.

## How the upstream list was derived

Mechanically, by reflecting over the installed package:

```sh
cd node && node -e 'const m = require("pbkdf2");
for (const k of Object.keys(m).sort()) console.log(k, typeof m[k], m[k].length)'
```

which prints exactly:

```
pbkdf2 function 6      # (password, salt, iterations, keylen, digest, callback)
pbkdf2Sync function 5  # (password, salt, iterations, keylen, digest)
```

The Go side was enumerated with `GOWORK=off go doc -all ./pwhash` in the passport
submodule.

## Deviations

Recorded per case in `cases/*.json` and in `passport/API-DEVIATIONS.md`.

1. **Degenerate raw-KDF parameters (4)** — `key-iterations-zero`,
   `key-iterations-negative`, `key-length-zero`, `key-length-negative`.
   `pwhash.Key` has no error return, matching the signature Go's PBKDF2 has
   always carried (`golang.org/x/crypto/pbkdf2.Key`): an iteration count below 1
   becomes 1 (the RFC 2898 minimum — never fewer), and a non-positive key length
   yields an empty key. Upstream throws for all four. This is reachable **only**
   through the raw KDF: the credential path refuses both, which
   `verify-iterations-zero` and `verify-iterations-negative` demonstrate by
   rejecting on *both* sides.
2. **Empty salt in a stored hash (1)** — `verify-empty-salt`. `pwhash.Decode`
   refuses a stored hash with a zero-length salt: `HashWithParams` cannot produce
   one, so it means corruption or tampering, and an unsalted hash is precisely
   what salting exists to prevent. Upstream has no encoded form and no such
   check, so it verifies the password against the unsalted key. The port is the
   stricter side and keeps the check.
