### Error messages

Upstream distinguishes four messages, all on the same `InvalidTokenError`:
`must be a string`, `missing part #N`, `invalid base64 for part #N`, and
`invalid json for part #N`. The port returns one sentinel, `ErrInvalidToken`,
for all of them. Per `parity/HARNESS.md` the harness matches on failure, not on
message text, so this is recorded here rather than scored: it is a message
difference, not a behavioural one. The `must be a string` case is unreachable in
Go, where `token` is typed `string`.

## Before → after

**41/45 = 91.11% → 45/45 = 100%.** Two port fixes closed the gap:

1. **Segment selection.** The port required exactly three dot-separated
   segments; upstream selects part #1 or #2 and never looks at the rest, so a
   two-segment string still yields a payload and a fourth segment is ignored.
   Cases `reject-two-segments`, `reject-four-segments`,
   `reject-header-two-segments`, `reject-header-single-segment`.
2. **base64 decoding.** The port now reproduces upstream's `base64UrlDecode`
   exactly — rewrite `-`/`_` onto `+`/`/`, pad up to a multiple of four, reject a
   length that is one more than a multiple of four — which means both alphabets
   are accepted, as upstream accepts them. Previously a payload encoded with the
   standard `+`/`/` alphabet was rejected.

## What the cases establish

- **No cryptography is involved and none is implied.** Every token in the corpus
  has an arbitrary signature segment; `decode-*` cases decode tokens that would
  never verify. That is the library's contract, and the package documentation says
  so.
- **The malformed corpus.** Missing segments, empty segments, `..`, invalid
  base64 characters, an impossible base64 length (`% 4 == 1`), truncated JSON,
  non-JSON, a BOM before the JSON, base64-of-base64, and a leading space or
  trailing newline that corrupts one segment but not another.
- **JSON shape.** `accept-json-null-payload` pins the one non-object payload both
  sides agree on (`null`); the other four are the declared deviation.
