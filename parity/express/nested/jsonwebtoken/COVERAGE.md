# `jsonwebtoken` → `github.com/malcolmston/express/jsonwebtoken`

Upstream oracle: **jsonwebtoken@9.0.3** (auth0/node-jsonwebtoken, pinned in
`node/package.json`). Measured score: `parity.json` — regenerated by
`GOWORK=off go test .`.

> **Security:** two findings from this harness are recorded in `security.json`
> (algorithm confusion, and an empty HMAC secret being usable). Both are cases
> where the port ACCEPTED a token upstream REJECTS; both are fixed in the express
> submodule, and the manifest exists so the released versions get an advisory.

## How the upstream inventory was derived

Mechanically, from the installed package:

```sh
node -e "console.log(Object.keys(require('jsonwebtoken')).sort().join('\n'))"
```


The option surfaces are enumerated from the source rather than from the README —
`sign` validates its options against a schema object, and `verify` reads its own
option names:

```sh
node -e "const s=require('fs').readFileSync('node/node_modules/jsonwebtoken/sign.js','utf8');
  console.log(s.match(/const sign_options_schema = \{[\s\S]*?\n\};/)[0]
    .split('\n').slice(1,-1).map(l=>l.trim().split(':')[0]).join(' '))"
# expiresIn notBefore audience algorithm header encoding issuer subject jwtid
# noTimestamp keyid mutatePayload allowInsecureKeySizes allowInvalidAsymmetricKeyTypes

node -e "const s=require('fs').readFileSync('node/node_modules/jsonwebtoken/verify.js','utf8');
  console.log([...new Set([...s.matchAll(/options\.([A-Za-z]+)/g)].map(m=>m[1]))].sort().join(' '))"
```

## Before → after

**89/120 = 74.17% → 120/120 = 100%.** The 31 cases that changed:

| fix | cases |
| --- | --- |
| **Algorithm confusion**: `Verify` (and `Sign`) refuse asymmetric key material as an HMAC secret → `ErrAsymmetricKey` | `rej-alg-confusion-rsa-pem-as-hmac-secret`, `rej-alg-confusion-rsa-with-hs-allowlist`, `rej-alg-confusion-ec-pem-as-hmac-secret` |
| **Empty secret** refused in both directions → `ErrMissingKey` | `rej-empty-secret-forgery`, `sign-empty-secret`, `sign-no-secret` |
| **Empty allowlist fails closed**: nil vs non-nil-empty `Algorithms`/`Issuer` | `rej-empty-allowlist`, `rej-empty-allowlist-hs512`, `rej-empty-issuer-list` |
| **Non-numeric `exp`/`nbf`** is a malformed token, not an absent constraint | `rej-string-exp`, `rej-string-exp-valid-signature`, `rej-null-exp`, `rej-string-nbf`, `rej-null-nbf` |
| **`ExpiresIn`/`NotBefore` measured from the payload `iat`** | `sign-expires-in-seconds`, `sign-not-before-seconds`, `sign-expires-and-not-before`, `sign-no-timestamp-with-expires-in` |
| **Option/claim conflicts refused** instead of overwriting | `sign-exp-claim-and-expires-in`, `sign-nbf-claim-and-not-before`, `sign-aud-claim-and-audience`, `sign-iss-claim-and-issuer`, `sign-sub-claim-and-subject`, `sign-jti-claim-and-jwtid` |
| **`NoTimestamp` drops an explicit `iat`** | `sign-no-timestamp-drops-explicit-iat` |
| **Ordered header and payload JSON** so the token bytes match | `sign-audience-string`, `sign-audience-array`, `sign-keyid`, `sign-all-options`, `sign-extra-header-params`, `sign-header-with-kid` |

## Declared deviations

| case(s) | deviation |
| --- | --- |
| `dec-two-segments`, `dec-empty-token`, `dec-malformed-base64` | `jwt.decode` returns `null` for a malformed token; `Decode`/`DecodeComplete` return `ErrInvalidToken`, which is how a Go caller is told |
| `dec-non-json-payload` | `Decode` returns `Claims` (a map), so a payload that is valid JSON but not an object is an error rather than a bare value |
| `sign-alg-none` | the port refuses the unsecured `none` algorithm outright; upstream can mint an unsigned token |
| `sign-hs256-with-public-key-pem` | the port refuses asymmetric key material as an HMAC secret when **signing** as well as verifying; upstream only refuses it on verify, so a Node caller can mint exactly the forgery its own `verify()` rejects |
| `sign-audience-single-element-array` | `Audience` is a `[]string`, so one entry is written as a JSON string (matching the common `audience: "x"`); Node's `audience: ["x"]` has no distinct Go spelling |
| `sign-negative-expires-in`, `sign-zero-expires-in` | a `time.Duration` has no "absent" value, so only a positive `ExpiresIn` counts as set; upstream honours zero and negative values |

## What the cases establish

- **Token bytes, not just semantics.** Every `sign-*` case compares the complete
  token string, so the header and payload JSON — key order included — must match
  upstream exactly. Payload claims are emitted in sorted key order followed by the
  option-derived claims (`iat`, `nbf`, `exp`, `aud`, `iss`, `sub`, `jti`), which is
  what upstream produces for a payload whose keys arrive sorted.
- **Cross-implementation verification.** Every token in the `verify` and `reject`
  groups was minted by the pinned upstream (or hand-forged with `crypto`), so
  acceptance means the port accepts real Node tokens and rejection means it
  refuses real forgeries.
- **The forgery corpus is the point.** 52 reject cases: algorithm confusion with
  RSA and EC public keys, `alg: none` (including the mixed-case `NoNe` spelling and
  an explicit `algorithms: ['none']`), an empty allowlist, an empty secret, a
  tampered `sub`, a tampered `exp`, a swapped header `alg`, a signature re-encoded
  into the standard base64 alphabet, truncated and extended signatures, a
  non-numeric `exp`/`nbf`, and every claim-assertion mismatch.
- **Determinism.** Every payload carries an explicit `iat` and every verification
  passes `clockTimestamp`, so no case depends on wall time.
