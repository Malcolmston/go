# `express/nanoid` vs `nanoid` — API coverage

- **Upstream (oracle):** `nanoid@6.0.1` (ai/nanoid), pinned in
  `node/package.json`.
- **Port:** `github.com/malcolmston/express/nanoid`.
- **Score:** see `parity.json`, regenerated by `GOWORK=off go test .`.

## Generated ids are never compared

An id is random, so no case compares one. Every `fn` in the two runners returns a
**deterministic property** of generation instead:

| property | how it is compared |
| --- | --- |
| the alphabet | returned verbatim as a string and compared directly (`alphabet-value`) |
| id length | code-point count for a given size (`len-*`, `custom-*`) — counted as code points on both sides, so a non-ASCII alphabet means the same thing in UTF-8 and UTF-16 |
| character set membership | every character of a generated id must be in the expected alphabet (`inalpha-*`, `custominalpha-*`) |
| reachable characters | the observed character set over 200–400 ids must equal the alphabet's distinct characters (`charset-*`) — a mask/reject bug that never selects the tail of the alphabet fails here |
| distinctness | 50 ids of the same size must all differ (`distinct-*`) |
| the size-0 identity | the empty id, compared as a value (`zero-id`, `customzero-*`) |
| rejection of an invalid size | both sides must fail (`neg-*`, `custom-neg-*`) |

## How the score is counted

`parity.json` separates three outcomes, and `go test` fails only on the middle
one:

- **match** — both implementations gave the same answer (or both failed).
- **mismatch** — they differed and the difference is *not* declared. This is a
  bug in the port; the harness reports it with `t.Errorf`.
- **deviations** — they differed and the case carries a `"deviation"` tag
  explaining why, which is also listed in the express submodule's
  `API-DEVIATIONS.md`. `../../../HARNESS.md` requires these to be counted
  separately from a bug, so they are excluded from `compared` and reported with
  `t.Logf`. `declaredDeviations` counts the tags; if it ever exceeds
  `deviations`, `staleDeviations` names the tags that describe a difference which
  no longer happens and should be deleted.

`parityPercent` is `match / compared`, i.e. over the cases where the two
implementations are expected to agree.

### Message-text differences

Upstream throws `Error("Wrong ID size")`; the port returns
`errors.New("nanoid: size must not be negative")` or
`errors.New("nanoid: alphabet length must be in 1..256")`. Text is not compared.

## Declared deviations

Listed in the express submodule's `API-DEVIATIONS.md`.

1. `custom-nonascii-03-len`, `custom-nonascii-03-inalpha`,
   `custom-nonascii-03-charset` — an alphabet of astral-plane emoji
   (`"🌮🌯🥑🌶"`). **Upstream is the outlier here.** `nanoid` indexes its
   alphabet with `alphabet[byte & mask]`, i.e. by UTF-16 code unit, so with a
   four-emoji alphabet it splices *halves* of surrogate pairs: it returns lone
   surrogates and fewer characters than requested (13 rather than 16 for
   `size: 16`). The port indexes code points and returns a well-formed id of
   exactly the requested length. Matching upstream would mean emitting invalid
   UTF-8.

## Untested

| surface | why |
| --- | --- |
| `customRandom(alphabet, size, getRandom)` | **The port exposes no deterministic-PRNG seam.** Upstream's third argument lets a caller substitute the byte source, so `customRandom("abcdef", 10, n => new Uint8Array(n).fill(3))()` deterministically returns `"dddddddddd"`. `nanoid.Custom` always reads from `crypto/rand` and takes no `io.Reader`, so there is no way to feed both sides the same bytes and compare the resulting id. Rather than invent a case that only one side can answer, this is recorded here: the only cross-language claim available about generation is the property set above, and the exact-id claim is untestable until the port grows such a seam |
| `random(bytes)` | not ported (`missing`); it is the seam above in raw form |
| an **empty** alphabet | upstream does not throw — it loops forever, because no byte index can ever be below `length 0`. `nanoid.Custom("", n)` returns an error. There is no comparable answer to a case that hangs one runner, so none was written; the difference (Go rejects, upstream hangs) is recorded here instead. The port is the safer of the two |
| an alphabet **longer than 256** characters | same situation: upstream hangs, the port returns an error. `custom-256-len` covers the documented maximum, which both sides accept |
| non-integer sizes (`nanoid(1.5)`) | upstream truncates to one character; Go's `int` parameter cannot receive `1.5`, so there is no shared input |

## Security review

Explicitly checked, because a weak id generator is the kind of finding that
belongs in a `security.json` rather than in a public issue. **No finding.** Read
against `express/nanoid/nanoid.go`:

- randomness comes from `crypto/rand.Read` only — there is no `math/rand` path
  and no fallback if the CSPRNG read fails (the error is returned);
- the alphabet is the same 64-character `urlAlphabet` as upstream, verified by
  direct string comparison in `alphabet-value`;
- the mapping is upstream's unbiased mask-and-reject, not a modulo, and the
  `charset-*` cases confirm the whole alphabet stays reachable for alphabets
  whose length is not a power of two (`abc`, `aaab`, `!@#$%^&*()`, 26 letters);
- the port is *stricter* than upstream on invalid alphabets (error where upstream
  loops).
