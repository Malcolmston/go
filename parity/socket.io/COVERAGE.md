# socket.io — upstream API vs `github.com/malcolmston/socketio`

- **Upstream (oracle), pinned exactly:** `socket.io@4.8.1`, `socket.io-client@4.8.1`,
  `socket.io-parser@4.2.7`, `engine.io-parser@5.2.3` (installed transitively:
  `engine.io@6.6.9`, `engine.io-client@6.6.6`). Node v24.18.0.
- **Go module under test:** `github.com/malcolmston/socketio v0.4.0` (published;
  no `replace`, resolved with `GOWORK=off go get …@latest`). Sub-packages
  `…/socketio/client` and `…/socketio/engineio` are part of the same module.
- **Score:** see `parity.json`, regenerated by `GOWORK=off go test ./parity/socket.io/`.

## What is actually being compared, and why

Socket.IO is a *specified wire protocol* plus a *behavioural contract*. Those are
the two things a port can get wrong, so the harness compares exactly those, in
three phases:

1. **Wire-protocol encoding (exact, highest value).** Both sides expose their
   codec, so no sockets are involved: `wire-encode` encodes a
   `(type, namespace, ack id, payload)` tuple and compares the resulting frames
   byte-for-byte; `wire-decode` feeds a corpus of *literal* wire strings and
   compares the parsed structure; `eio-frame` does the same for the Engine.IO v4
   framing underneath (single packets and `\x1e`-separated polling payloads).
   This is fully deterministic and is where binary attachment placeholders and
   namespace/ack ordering are pinned down. **The port does export its codec**
   (`socketio.Encoder`/`Decoder`, `Packet.Encode`/`EncodeBinary`,
   `DecodePacket`, `engineio.Encode`/`Decode`/`EncodePayload`/`DecodePayload`),
   so no proxying was needed. One limitation: `Packet.attachments` is
   **unexported and settable only by `EncodeBinary`**, so a caller cannot
   construct a `BINARY_EVENT` with a chosen attachment count — that encoder path
   is therefore untestable from outside the package.
2. **Observable end-to-end behaviour (`behaviour`).** Each runner starts its own
   server on a random `127.0.0.1` port, connects with its **own** client over the
   websocket transport, and emits an ordered transcript for a scripted scenario:
   argument marshalling, ack callbacks, namespaces with accepting/rejecting/silent
   middleware, rooms and broadcast (including sender exclusion), `onAny`, binary
   payloads in both directions, handler removal, socket-scoped data, and
   disconnect reasons.
3. **Cross-implementation interop (`interop`) — the strongest evidence here, and
   it works.** The harness pairs a server from one implementation with a client
   from the other: upstream JS client → Go server, Go client → upstream JS
   server, and Go → Go, each compared against the all-upstream pairing. All
   three pairings reproduce the upstream server *and* client transcripts exactly.
   The port's handshake, Engine.IO framing, CONNECT/EVENT/ACK/BINARY_EVENT/
   BINARY_ACK/DISCONNECT handling and namespace negotiation are therefore
   genuinely wire-compatible with real Socket.IO in both directions. (The Go
   client is websocket-only, so the interop script uses
   `transports: ["websocket"]` on the JS side too; polling and the
   polling→websocket upgrade are *not* covered by this harness.)

### Normalisation (exactly what is replaced)

Only these volatile values are normalised; everything else is compared literally.

| volatile value | placeholder | why |
| --- | --- | --- |
| server-assigned socket id | `<S1>`, `<S2>`, … in first-seen order | random per run |
| a socket's implicit self-room (`room === socket.id`) | `<self>` | random per run |
| listening TCP port | never enters a transcript (URLs are passed between runners, not reported) | random per run |
| Engine.IO session id (`sid`) | never enters a transcript | random per run |
| the port's client error prefix `"client: "` | stripped | so the message compares with upstream `Error.message` |
| a handshake that never completes | `<no reply>` (upstream's `timeout` connect_error, the port's `connect timeout`) | different wording for the same observation |
| the port's client `"disconnect"` event, which carries no reason | `<no-reason>` | records the missing argument rather than hiding it |
| broadcast fan-out lines (`cli:heard …`) | sorted | delivery order across different sockets is unspecified |

Timestamps do not appear anywhere. Binary payloads are always reported as
lowercase hex inside a `{"$bin":"…"}` marker, on both sides.

## How the upstream inventory was derived

Mechanically, by walking the real installed prototypes — not from the README:

```
cd parity/socket.io/node && node enum.mjs          # all classes
cd parity/socket.io/node && node enum.mjs Server   # one class
```

`enum.mjs` walks `Reflect.ownKeys` up each prototype chain of `Server`,
`Namespace`, `Socket` (server), `BroadcastOperator` (reached through a live
`io.to(...)` instance — it is not exported), `Socket` (client) and `Manager`,
plus `Object.keys` of the `socket.io-parser` / `engine.io-parser` module
namespaces. It skips `_`-prefixed members and generic `EventEmitter` plumbing.

The tables below cover every member that walk reports **except** the ones listed
under "excluded as internal" at the end of each table; those are implementation
hooks with no documented contract and are not part of the denominator.

## Divergences found

### Wire format (highest severity — these are protocol bugs)

- **W1 `enc-event-key-order`, `enc-connect-error-nsp` — object keys are
  reordered on the wire.** Go's `json.Marshal` sorts map keys; JavaScript
  preserves insertion order. `{"b":1,"a":2,"C":3}` goes out as
  `{"C":3,"a":2,"b":1}`. Semantically equivalent JSON, but not byte-identical,
  so any signature/digest over the frame differs.
- **W2 `enc-event-html-chars` — `<`, `>` and `&` are escaped.** `Packet.Encode`
  uses plain `json.Marshal`, whose HTML escaping is on by default: `"a<b>&c"`
  becomes `"a<b>&c"` on the wire where upstream emits the raw
  characters. Fix: `json.Encoder` with `SetEscapeHTML(false)`.
- **W3 `enc-event-negative-zero` — `-0` is emitted as `-0`**, upstream as `0`.
- **W4 `enc-type-out-of-range` — Go rejects a packet type > 6** with
  `ErrInvalidPacket`; upstream's encoder emits `"7[\"x\"]"` without complaint.
  (Go is arguably more correct, but it is a behavioural difference.)
- **W5 `enc-binary-in-connect` — buffers are extracted from non-EVENT/ACK
  packets.** `EncodeBinary` deconstructs the payload *before* checking the type,
  so a `[]byte` inside a CONNECT payload is replaced by a placeholder and an
  attachment frame is emitted — while the text header keeps type `0` and carries
  **no attachment count**, producing an unparseable packet. Upstream only
  promotes EVENT/ACK and serialises the buffer inline. This can only be reached
  by a caller building a Packet by hand, not by `Socket.Emit`.
- **W6 `dec-binary-event-complete`, `dec-binary-event-two`,
  `dec-binary-event-nsp-ack`, `dec-binary-ack-complete` — a reassembled binary
  packet keeps type `BINARY_EVENT`/`BINARY_ACK` (5/6).** Upstream's
  `Decoder.add` rewrites the type to `EVENT`/`ACK` (2/3) as soon as the header is
  decoded, so every consumer sees a plain EVENT. `codec.go`'s doc comment claims
  the port's behaviour "mirrors socket.io-parser" — it does not. Any code
  switching on `pkt.Type` after `Decoder.Add` must special-case 5/6 (the port's
  own `conn.go` and `client.go` do exactly that, internally).
- **W7 `dec-connect-array-payload`, `dec-connect-error-array`,
  `dec-connect-null-payload` — payload validation is too permissive.**
  Upstream validates with `isObject()` (`[object Object]`), which rejects arrays
  and `null`; the port's `isPayloadValid` accepts `[]any` and `nil` for CONNECT
  and CONNECT_ERROR. `0[1]`, `4[1]` and `0null` are accepted where upstream
  throws "invalid payload". The Go source comment describing the JS rule as
  `typeof payload === "object"` is the origin of the mistake.
- **W8 `dec-binary-placeholder-out-of-range` — an out-of-range placeholder is
  silently kept.** For `51-[…{"_placeholder":true,"num":3}]` with one attachment,
  upstream throws "illegal attachments"; `Reconstruct` leaves the placeholder
  object in the payload, so the application receives
  `{"_placeholder":true,"num":3}` as if it were data.
- **W9 `dec-binary-zero-attachments` — `5`/`6` with a `0-` attachment count is
  accepted.** Upstream rejects `50-["b"]` ("Illegal attachments"); the port
  decodes it as a complete BINARY_EVENT and reports itself not pending.
- **W10 `dec-attachments-cleared` — `attachments` is not cleared after
  reassembly.** Upstream sets it to `undefined`; `Packet.Attachments()` still
  returns the original count on a fully reassembled packet.
- **W11 `dec-empty-frame` — an empty frame.** Upstream decodes `""` as a CONNECT
  to `/` (`Number("") === 0`); the port returns `ErrInvalidPacket`. Go is more
  defensible; it is still a difference.
- **W12 `eio-dec-binary-bad-base64` — invalid base64 in a `b…` frame.** Node's
  `Buffer.from(s, "base64")` is lenient and yields an empty buffer;
  `base64.StdEncoding.DecodeString` errors. Go is stricter.
- **W13 `eio-decpay-empty` — an empty polling body.** Upstream's `decodePayload("")`
  produces a `parser error`; `engineio.DecodePayload("")` returns an empty packet
  list with no error.

### Behaviour

- **B1 `emit-scalar-args` — events are delivered out of order.** `conn.handleEvent`
  dispatches every inbound packet with `go socket.dispatch(pkt)`, so five
  back-to-back `emit`s on one socket arrive in an arbitrary order (observed:
  `done` first). Socket.IO guarantees ordered delivery within a socket; this is
  the most consequential behavioural bug found, because it silently breaks any
  protocol built on event sequencing.
- **B2 `ack-no-handler`, `ack-handler-never-calls` — the port acks an event that
  nothing handled.** `Socket.dispatch` sends an ACK whenever `pkt.ID != nil`,
  substituting `[]` when no handler returned a value. Upstream only acks when a
  handler actually invokes its callback. Consequences: (a) an **ack timeout is
  unreachable Go-to-Go**, so a client can never detect an unhandled event; (b) a
  caller **cannot distinguish "handled, nothing to report" (`cb()`) from "no
  handler at all"** — both arrive as `[]`.
- **B3 `server-ack-no-handler` — the same defect in the client.**
  `client.Client.dispatch` auto-acks identically, so `Socket.EmitAck`'s timeout
  is also unreachable when the peer is a Go client.
- **B4 `namespace-middleware-silent` — middleware that never calls `next()`
  connects the socket anyway.** `Namespace.runMiddleware` breaks out of the chain
  when `next` was not called but returns a `nil` error, so the connection is
  accepted and the connection handler runs. Upstream leaves the handshake
  unanswered (the client times out). A "hold the connection then decide later"
  middleware therefore becomes an unconditional accept — a security-relevant
  difference.
- **B5 `disconnect-server-namespace` — the port's client never learns about a
  namespace-level disconnect.** `Socket.Disconnect(false)` sends a DISCONNECT
  packet, but `client.handleSioPacket` has **no case for `socketio.Disconnect`**,
  so it is dropped: no `disconnect` event, no state change.
- **B6 `disconnect-namespace-then-emit` — events sent after a namespace
  disconnect are still delivered to the port's client** (`cli:after` fires),
  because the client keeps no per-namespace connected state. Upstream ignores
  them.
- **B7 `disconnect-server-transport` — the client's `disconnect` event carries no
  reason.** Upstream reports `"io server disconnect"`; `Client.fireLocal("disconnect")`
  passes no arguments.
- **B8 `disconnect-client-initiated` — no `disconnecting` event.** Upstream fires
  `disconnecting` (while the socket is still in its rooms) before `disconnect`;
  the port has only `OnDisconnect`.
- **B9 `reserved-event-server-emit`, `reserved-event-client-emit` — the reserved
  event-name guard is never applied.** Both `Socket.Emit` and `client.Client.Emit`
  happily send `connect`, `disconnect` and `connect_error` as application events,
  which upstream rejects by throwing. The port *has* `ValidateEventName`/
  `IsReservedEvent` — nothing calls them.

### What the port lacks (API-level, no case possible)

- Client: **no catch-all** (`onAny`/`prependAny`/`offAny`/`listenersAny`), **no
  handler removal** (`off`/`once`), no outgoing catch-all, no
  `connected`/`disconnected`/`active`, no manual `connect()`, no Manager, no
  polling transport and no transport upgrade — one `Client` is one namespace over
  one websocket.
- Server: no `Socket.use` (per-packet middleware), no outgoing catch-all, no
  `disconnecting` event, no `Socket.connected`/`disconnected`, no
  `Socket.request`/`conn`, no full `handshake` (only `auth`), no
  `BroadcastOperator.emitWithAck`/`fetchSockets`/`socketsJoin`/`socketsLeave`/
  `disconnectSockets`, no `serverSideEmitWithAck`, no `connectTimeout`, no
  `serveClient`, no `Server.engine`.
- `compress`, `volatile` and `timeout` exist on `BroadcastOperator` but are
  recorded and never acted on.
- `Packet.attachments` is unexported, so a `BINARY_EVENT` cannot be encoded from
  a hand-built packet; upstream's `encodeAsString` path for an explicit
  attachment count is unreachable from outside the package.
- Upstream's `encodePayload([])` never invokes its callback (an upstream quirk
  with no Go equivalent), so that input has no comparable case.
