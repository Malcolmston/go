# handlebars — upstream API inventory vs the Go port

- **Upstream oracle:** `handlebars@4.7.8` (npm, pinned in `node/package.json`; `node -e "console.log(require('handlebars/package.json').version)"` → `4.7.8`)
- **Go port:** `github.com/malcolmston/handlebars v0.0.0-20260810111532-be93e3763eef` (resolved by `GOWORK=off go get github.com/malcolmston/handlebars@latest`)
- **Harness:** `GOWORK=off go test ./parity/handlebars/` — both runners are subprocesses speaking JSON Lines; `parity.json` is regenerated by the test.

## How the upstream symbol list was derived

Mechanically, from the installed package — not from the README:

```sh
cd parity/handlebars/node
node -e "const H=require('handlebars');
  console.log('TOP:',        Object.keys(H).sort().join(' '));
  console.log('HELPERS:',    Object.keys(H.helpers).sort().join(' '));
  console.log('DECORATORS:', Object.keys(H.decorators).sort().join(' '));
  console.log('UTILS:',      Object.keys(H.Utils).sort().join(' '));
  console.log('PARTIALS:',   Object.keys(H.partials).sort().join(' '));"
```

which prints exactly:

```
TOP:        AST COMPILER_REVISION Compiler Exception HandlebarsEnvironment JavaScriptCompiler
            LAST_COMPATIBLE_COMPILER_REVISION Parser PrintVisitor REVISION_CHANGES SafeString
            Utils VERSION VM Visitor __esModule compile create createFrame decorators default
            escapeExpression helpers log logger noConflict parse parseWithoutProcessing partials
            precompile print template
HELPERS:    blockHelperMissing each helperMissing if log lookup unless with
DECORATORS: inline
UTILS:      __esModule appendContextPath blockParams createFrame escapeExpression extend indexOf
            isArray isEmpty isFunction toString
PARTIALS:   (empty — no partials are registered by default)
```

The compile-option list was derived the same way, from the installed source rather than the docs:

```sh
grep -ohE "options\.(compat|data|knownHelpers|knownHelpersOnly|noEscape|strict|assumeObjects|preventIndent|ignoreStandalone|explicitPartialContext|trackIds|stringParams|srcName|destName)\b" \
  node_modules/handlebars/lib/*.js node_modules/handlebars/lib/**/*.js | sort -u
```

The Go side was enumerated with `GOWORK=off go doc -all github.com/malcolmston/handlebars` and, for the
helper registry, `handlebars.New().HelperNames()` → `and eq gt gte log lookup lt lte ne not or`
(`if`/`unless`/`each`/`with` are implemented in the renderer rather than the registry, and
`HasHelper` reports them as absent).

## Counts

Enumerated upstream symbols and options: **66** (32 top-level exports + 8 built-in helpers + 1 decorator + 11 `Utils` members + 14 compile options).

| status | count |
| --- | --- |
| match | 22 |
| differs | 6 |
| untested | 3 |
| missing | 35 |
| extra (Go-only, not in the 66) | 7 rows |

- **Symbol parity over symbols actually compared:** 22 / (22 + 6) = **78.6 %**.
- **Symbol parity over everything upstream exports:** 22 / 66 = **33.3 %** — dominated by the compiler/precompiler/AST-visitor surface (`Compiler`, `JavaScriptCompiler`, `precompile`, `template`, `Visitor`, `print`, revision constants), which a pure-Go template engine has no reason to expose.
- **Case total: 236 cases** across 8 case files; **207 match (87.7 %)**, 29 mismatch, 0 declared deviations. 15 of the matches are cases where *both* implementations fail, which is parity.
- Error *messages* are never compared — only whether each side failed. Upstream messages are jison parse errors with line/column carets; the port's are short `handlebars: …` strings.

## Behavioural divergences found (all 29 failing cases)

Value formatting (`Stringify`/`escapeExpression`) — 11 cases:

| case | upstream | Go |
| --- | --- | --- |
| `val-large-integer` | `1000000` | `1e+06` |
| `val-small-fraction` | `0.000001` | `1e-06` |
| `val-object` / `val-object-escaped` | `[object Object]` | `map[a:1]` |
| `val-empty-object` | `[object Object]` | `map[]` |
| `val-array-of-strings` | `a,b,c` | `[a b c]` |
| `val-array-of-numbers` | `1,2,3` | `[1 2 3]` |
| `val-array-empty` | `` (empty) | `[]` |
| `val-array-nested` | `1,2,3` | `[[1 2] [3]]` |
| `val-array-with-null` | `1,,3` | `[1 <nil> 3]` |
| `val-array-of-objects` | `[object Object]` | `[map[a:1]]` |
| `esc-expr-array` / `esc-expr-object` | `&lt;a&gt;,b` / `[object Object]` | `[&lt;a&gt; b]` / `map[a:1]` |

The port formats floats with `strconv.FormatFloat(v,'g',-1,64)`, which switches to exponent form
where JavaScript's `Number#toString` does not, and falls back to `fmt.Sprintf("%v")` for composite
values instead of JS `Array#toString` / `Object#toString`.

Parser strictness — 5 cases (upstream throws, the port accepts):

| case | template | upstream | Go |
| --- | --- | --- | --- |
| `path-array-index` | `{{items.0}}` | parse error (`Expecting 'ID', got 'NUMBER'`) | `a-c-[]` — the port accepts unbracketed numeric segments |
| `malformed-empty-mustache` | `{{}}` | parse error | renders empty |
| `malformed-unclosed-subexpr` | `{{shout (shout a}}` | parse error | renders `X` |
| `malformed-bad-hash` | `{{shout k=}}` | parse error | renders empty |
| `block-mismatched-close-throws` | `{{#if a}}x{{/each}}` | `if doesn't match each` | renders `x` |

Path/scope resolution — 3 cases:

- `path-parent-one-nested-each` / `path-parent-two`: with two nested `{{#each}}`, upstream reaches the
  root at `../`, the port needs `../../`. The port counts one more frame per nested `each` than upstream.
- `path-parent-beyond-root`: `{{../x}}` at top level gives `` upstream, `root` in the port — the port
  clamps `../` at the root frame instead of walking off it.

Other — 10 cases:

- `each-object-insertion-order`: upstream iterates object keys in insertion order (`z;a;m;`), the port
  sorts them (`a;m;z;`). Inherent: a Go `map` has no insertion order, and the port documents sorting as
  deliberate determinism.
- `opt-nodata` / `opt-nodata-root`: `compile(src,{data:false})` in 4.7.8 still yields `@index` and
  `@root`; `handlebars.NoData()` genuinely suppresses them. The port is arguably more correct here, but
  it is not parity.
- `opt-compat-parent-scope-lookup`: no `compat` option in the port at all.
- `partial-bracketed-name`: `{{> [my part]}}` — upstream resolves the bracketed partial name, the port
  errors with `unknown partial "[my part]"` (brackets are not stripped for partial names).
- `partial-dynamic-bare-subexpr`: `{{> (which)}}` — upstream treats `(which)` as a helper call and
  throws; the port resolves it as a path and renders the partial.
- `raw-block`: `{{{{raw}}}}{{escaped}}{{{{/raw}}}}` — upstream passes the raw body to a `raw` helper
  (absent here, so the output is empty); the port emits `}E}`, i.e. it neither treats the body as raw
  text nor dispatches to a helper. This looks like a lexer bug in the port.
- `helper-block-body-uses-context`: `{{#bold}}{{v}}{{/bold}}` where the helper renders its body with the
  current context. JS writes `options.fn(this)`; the Go `Options` type exposes **no accessor for the
  current context**, so the closest available call is `o.Fn(nil)` and the body loses its context
  (`<b></b>` instead of `<b>V</b>`). This is an API gap, not just a behaviour difference.

## Upstream features the port lacks

- Compile options `compat`, `assumeObjects`, `preventIndent`, `ignoreStandalone`,
  `explicitPartialContext`, `trackIds`, `stringParams`, `srcName`, `destName`.
- Precompilation and the precompiled-template runtime (`precompile`, `template`, `Compiler`,
  `JavaScriptCompiler`, `COMPILER_REVISION`, `REVISION_CHANGES`, `LAST_COMPATIBLE_COMPILER_REVISION`).
- AST access and traversal (`parse` returning an AST, `parseWithoutProcessing`, `Visitor`,
  `PrintVisitor`, `print`, `AST` builders).
- `Exception`, `logger`/`logger.level`, `log()`, `noConflict`, `VERSION`.
- `Utils.appendContextPath`, `Utils.blockParams`, `Utils.indexOf`, `Utils.isFunction`, `Utils.toString`.
- Function-valued context members (upstream calls them; `Utils.isFunction` exists for that) — untestable
  through a JSON case file, so not scored.
- Decorators cannot replace the program function: `Decorator func(*DecoratorOptions)` returns nothing,
  so only side-effecting decorators (like the built-in `inline`) are expressible.
- No accessor for a block helper's current context (`this` in JS).
